# Frontend and End-to-End Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a Chinese React interface for historical K-lines, schema-driven custom indicators, Task scheduling/history, and hot system settings, then verify the complete user flows.

**Architecture:** React owns selection and indicator instance state; Lightweight Charts owns one shared time axis and native panes. Backend versioned DTOs pass through a typed adapter, while schema-driven forms and consistent API error handling avoid per-indicator frontend code.

**Tech Stack:** React, TypeScript, Vite, React Router, TanStack Query, Ant Design, Lightweight Charts 5.2, React JSON Schema Form, Vitest, Testing Library, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-05-local-stock-indicator-system-design.md`, `docs/superpowers/plans/2026-11-05-backend-core.md`, and `docs/superpowers/plans/2026-11-05-market-data.md`

## Global Constraints

- Create only `frontend/` plus the documented production static mount; do not modify existing indicator/validation directories or root package/test files.
- Use Lightweight Charts 5.2 APIs: `chart.addSeries(...)`, numeric pane indexes, and `createSeriesMarkers(...)`; never mix v4 `addLineSeries` or `series.setMarkers` examples.
- Every feature follows RED → GREEN → refactor; frontend line coverage is at least 80%.
- Indicator and Task forms come from backend schemas; adding a backend indicator requires no new React component.
- All remote text renders as plain text; no `dangerouslySetInnerHTML`, arbitrary HTML tooltips, or unbounded API responses.
- Do not automatically commit or push; Git operations require a separate explicit user request.

## Review Focus

1. A marker whose date has no actual K-line must be surfaced as an error/test fixture failure, not silently dropped by Lightweight Charts: Task 2 validates adapter input and Task 5 checks visible signals.
2. Null indicator values must become whitespace, while NaN/infinity and duplicate dates are rejected before canvas rendering: Task 2 tests each input.
3. Removing or reordering indicators must detach marker plugins and remove stale panes without deleting the main candle series: Task 2 tests complete cleanup.
4. API failure, revision conflict, rate limiting, partial indicator failure, and empty initial databases need visible non-destructive UI states: Tasks 1, 3, and 4 test them.
5. Cron edits, immediate runs, and hot settings must preserve server revisions and never overwrite a newer config from another tab: Task 4 tests 409 refresh/retry behavior.
